# 판교어 스팬 탐지기(Create ML `MLWordTagger`) 실험 보고서

- 날짜: 2026-10-26 · 측정 기기: MacBook (Apple M3), macOS 26 / Xcode 26.4 SDK / Swift 6.3
- 질문: "Foundation Models / Core ML 로 우리만의 판교어 모델을 학습할 수 없나?"
- 전제(이전 조사): FM 어댑터 툴킷 26.0.0이 마지막 버전이고 iOS 27과 호환되지 않음 → **FM 파인튜닝 불가**. Core ML은 실행 엔진이지 LLM 학습 도구가 아님.
- 이 실험이 확인한 것: **"설명하는 LLM"이 아니라 "판교어가 어디 있는지 찾는 작은 태거"는 Mac에서 Create ML로 학습해 iOS 17+에 실을 수 있다.** 쉬운 말 설명은 지금처럼 서버(사전 → AI)나 FM이 맡는다.
- 코드·데이터·모델: `ml/pangyo-tagger/` (스크립트만 커밋. 데이터·모델 29MB는 `gen.py`(시드 고정)로 다시 만든다. 합성 데이터만 → ADR-0008)

## 2. 방법

### 2-1. 합성 데이터 (실사용자 문장 0)
- 서버 사전 시드(#12 Day 6)가 아직 없어서 **실험용 사전 145개 용어**를 직접 만듦 (`terms.py`): 표준 표기 + 사전 이형 표기(영문·한글 변형, 예: 싱크/sync/씽크) + **사전에 없는 '새 표기'**(싱크업, SYNC, 디벨롭먼트, 우선 순위…).
  - 그중 **15개 용어는 학습·사전 둘 다에서 뺌**(트레이드오프, 레드팀, 러닝커브, 엣지케이스…) → "사전에 없는 신규 판교어"를 흉내.
  - 사전 시뮬레이션 = 130개 용어 × 표기 = **371항목**.
- 생성기 `gen.py` (`python3 -I`, seed 20261026, 결정적): 짧은 조각(고정 어절 ≤ 2)을 이어 붙여 Slack/회의 말투 문장을 만듦. 조사는 받침에 맞춰 붙이고(`얼라인을`, `ASAP으로`), 하다 활용(`싱크해서`, `디벨롭하실래요`)을 붙임. **정답 스팬은 용어 표기만**(조사·활용 제외), 인덱스는 **유니코드 스칼라 0-시작·끝 미포함** = `eval/dataset/README.md`·REQ-14 좌표계.
- **3-gram 중복 0**: 테스트 문장의 어절 3-gram이 하나라도 겹치는 학습 문장은 버림(7,321개 버리고 4,000개 채택). 검증 결과 train∩test 3-gram = 0.
- 사전 문자열이 템플릿 고정어에 섞여 정답과 어긋나던 3곳(`다음 스프린트에`, `깃헙 이슈에`, `미팅 잡아주세요`)을 발견해 고침.

### 2-2. 한국어 토큰화 (가장 중요한 설계 결정)
`NLTokenizer(.word)` 실측: `["이번","스프린트","얼라인을","하고","싱크해서","R","R","정리해요"]` — **조사·활용이 붙은 어절 단위**이고 `R&R`은 쪼갬. 정답은 `얼라인`(조사 제외)이라 어절 토큰으로는 끝 위치를 바로 못 얻는다. 두 방식을 비교:

| 방식 | 토큰 | 스팬 복원 | 비고 |
|---|---|---|---|
| **C (글자)** | 공백 아닌 스칼라 1개 = 토큰, 어절 첫 글자에 `▁` 접두 | 토큰 i ↔ 스칼라 i **1:1, 손실 0** (oracle 오류 0) | 조사 경계를 모델이 직접 학습 |
| **W (어절+문자종류)** | 공백 + 한글/라틴/기호 경계로 자름(`develop하실래요`→`develop`,`하실래요`), `R&R` 유지 | 마지막 토큰에서 조사·하다 활용 접미 규칙으로 잘라냄 | 규칙 한계로 정답을 넣어도 문장 1~2%는 어긋남(oracle 오류 test_seen 9/500) |

- 학습·추론 모두 **우리가 만든 토큰 배열**을 쓰고 `NLModel.predictedLabels(forTokens:)`(iOS 12+)로 예측 → NLTagger의 자체 토큰화에 의존하지 않음.
- Swift 토큰화 스케치(`tokcheck.swift`, `String.unicodeScalars` 기준)가 Python과 **10,900문장 토큰 100% 일치** → 앱에서 계산한 인덱스가 서버 `startIndex/endIndex`와 같은 좌표계임을 확인.

### 2-3. 학습 (Create ML, `xcrun swift train.swift <C|W> <crf|bert> [train_v2|train_v3]`)
- API 확인(sosumi + SDK `.swiftinterface`): `MLWordTagger.ModelAlgorithmType = .crf(revision:)` | `.transferLearning(FeatureExtractorType, revision:)`, `FeatureExtractorType = .elmoEmbedding | .bertEmbedding(macOS 14+) | .dynamicEmbedding(폐기)`. `language: .korean` 지정.
- `.bertEmbedding` = `NLContextualEmbedding`(Apple 다국어 BERT, 512차원). 이 Mac에서 `NLContextualEmbedding(language: .korean).hasAvailableAssets == true` → 한국어 학습 가능 확인. ELMo는 비용 대비 의미 없어 생략.
- 저장 `.mlmodel` → `MLModel.compileModel` → `NLModel(contentsOf:)` = 앱 번들과 같은 경로로 로드해서 예측.

### 2-4. 평가
- 스팬 **exact match**(start·end 둘 다) micro P/R/F1 = `eval/run.py score_term_spans` 규칙과 같음.
- 베이스라인 = 사전 트라이 최장 일치: `dict_naive`(아무 위치) / `dict_boundary`(어절·문자종류 경계에서만 시작, 대소문자 무시).
- 하이브리드:
  - A `dictwins`: 사전 스팬 + 겹치지 않는 모델 스팬
  - B `longest`: 겹치면 더 긴 쪽(모델이 `얼라인업`을 잡으면 사전의 `얼라인`을 대체)
  - **C `longest+conf0.9`**: B와 같되 모델 스팬은 토큰 최소 확률 ≥ 0.9(`predictedLabelHypotheses(forTokens:maximumCount:)`, iOS 14+)만. **임계값 0.9는 사전에 정했고 테스트로 튜닝하지 않음**
  - D `veto`: C + 모델이 확률 ≥ 0.9로 전부 O라고 보는 사전 스팬은 버림(동음이의 거부)

### 3-2. 읽는 법
1. **사전에 있는 표기는 사전이 정답이다.** 모델 단독은 seen에서 0.96~0.99로 오히려 낮다. → 모델이 사전을 대신할 이유가 없다(REQ-14 "사전 우선"과 일치).
2. **모델의 가치는 사전 밖에 있다.** 새 표기 0.06 → 0.90, 신규 용어 0.00 → 0.86 (하이브리드 C + W-BERT v3). 사전은 `얼라인업`을 `얼라인`으로 잘못 자르거나(오탐) 못 찾는다.
3. **가장 큰 위험 = 평범한 명사 오탐.** v1 모델은 "조사 붙은 슬롯 자리 = 판교어"를 외웠다: 일반어 300문장에 C-CRF 188건, W-BERT 396건 오탐. 학습에 일반어 하드 네거티브를 40% 넣고(v3) + 확률 0.9 게이트를 걸면 16건(CRF)/49건(BERT)까지 준다. **합성 데이터의 일반어 어휘가 작아서 생긴 문제라 실제 문장에서는 더 나빠질 수 있다** — 출시 전 최대 검증 항목.
4. **동음이의(함정)는 사전이 12/12 전부 틀린다**(축구 `킥오프`, `콜`라, `린`넨, `이슈`타르). 문맥을 보는 W-BERT는 혼자서 2~7건만 틀리고, D(veto)로 사전 오탐을 12 → 6으로 절반 줄인다. CRF는 문맥이 짧아 이 효과가 없다.
5. 글자(C) vs 어절(W): CRF는 **C가 낫다**(새 템플릿에 강하고 조사 경계를 직접 학습). BERT는 **W가 낫다**(BERT는 어절 문맥을 봐야 의미가 있음; C-BERT는 새 템플릿 0.71). W는 접미 규칙 한계(정답을 넣어도 1~2% 어긋남)가 있다.
6. **과대평가 경고**: 템플릿 합성이라 문맥이 단순하다. 새 템플릿 세트도 같은 생성기에서 나왔다. 이 숫자는 "가능성 확인"이지 품질 약속이 아니다.

## 4. 앱·서버에 끼우는 방법

### 4-1. 앱 (iOS 17+, Tuist 모듈 규칙 ADR-0001)
```
Domain   : protocol JargonDetecting { func detect(_ text: String) -> [JargonSpanHint] }   // Foundation만
           struct JargonSpanHint { start: Int; end: Int; matchedText: String; confidence: Double; source: .dictionarySnapshot | .model }
Platform : JargonDetector (NaturalLanguage + CoreML)
           - 번들 리소스 PangyoTagger.mlmodel (Xcode가 .mlmodelc로 컴파일), NLModel(contentsOf:) 지연 로드 1회
           - 토큰화 = unicodeScalars 기준 (tokcheck.swift 스케치), predictedLabelHypotheses(forTokens:maximumCount:)로 확률
           - 확률 < 0.9 버림, 사전 스냅샷(있으면) 우선 + longest 병합
           - BERT 판: NLContextualEmbedding(language:.korean).hasAvailableAssets 확인, 없으면 requestAssets 또는 CRF 판으로 폴백
Feature  : 결과는 "미리보기 형광펜(점선/옅은 색)" — 저장 안 함, 서버 응답 도착 시 서버 스팬으로 교체
```
- 네트워크 0(원문이 기기 밖으로 안 나감), `URLSession` 의존 0 → 15-4 표의 "② FM / ③ MLX" 행과 같은 보장.
- 크기: CRF 0.45 MB / BERT 1.5 MB → 앱 크기 영향 무시 가능.

### 4-2. 서버 (정본은 여전히 서버, REQ-14)
- **정본 = 서버 사전 우선 + 서버 인덱스 재계산**. 온디바이스 결과는 정본이 될 수 없다(ADR-0007).
- 온디바이스 탐지기의 역할 3가지:
  1. **미리보기**: 서버 왕복 전 형광펜 미리 표시(쉬운 말 설명은 없음 또는 FM 미리보기).
  2. **오프라인 모드**: 네트워크 없을 때 "판교어 N개 찾음 — 연결되면 설명" 상태.
  3. **신규 용어 후보 수집(v1.2+, 옵트인)**: 사전에 없는데 모델이 잡은 스팬의 *용어 문자열만*(문장 X) 운영자 검수 큐로 → 사전 보강. v1.1 계약의 `clientHints`/`engineHint`(§11 #11)와 같은 통로를 쓰되 원문은 안 보냄.
- 같은 모델을 서버에서도 돌릴 수 있나: Create ML 모델은 Apple OS 전용 → 서버(리눅스)에서는 불가. 서버 쪽 "새 표기" 보강은 사전 이형 표기 추가 + 정규화(대소문자·띄어쓰기 무시)로 먼저 하는 게 싸다.

## 5. 영어(이중 언어) 판단
- 판교어는 **한국어 문장 안의 한국식 외래어·약어**라서, 탐지 대상 텍스트는 언어 UI와 상관없이 한국어다. 영어 UI 사용자(예: 한국 회사에 다니는 외국인)도 **같은 한국어 탐지기**를 쓰면 된다.
- 영어 현지화 = UI 문자열(String Catalog) + **설명문(plainKo → plainEn)** 문제. 설명은 서버 사전에 `plain_en` 열(또는 번역 테이블)을 두고 AI 폴백도 영어 출력 옵션을 주는 쪽. 탐지 모델을 언어별로 만들 필요 없음.
- 영어 문장 속 업무 은어(예: "let's circle back", "boil the ocean")는 **다른 제품 문제**(별도 사전·별도 태거, `language: .english`, ELMo/BERT 둘 다 가능). 지금 범위 밖, 수요 확인 후.

## 부록: ADR-0018 초안

# ADR-0018: 판교어 "탐지"는 Create ML 태거로 온디바이스 보조, "설명"은 서버(사전 → AI)·FM이 맡는다. 정본은 서버

- 상태: 제안 (2026-10-26)
- 관련: REQ-10(④ 자체 소형 모델의 현실적 형태), REQ-14, REQ-33 / ADR-0007·0008 / 14번 §15-1·§15-6 / 이슈 #12(사전 시드·트라이), #72(F-15 FM), #75(계약 v1.1 `clientHints`)

## 맥락
사용자 질문 "Foundation Models / Core ML로 우리 판교어 모델을 학습할 수 없나?". FM 어댑터 툴킷은 26.0.0이 마지막이고 iOS 27과 호환되지 않아 FM 파인튜닝은 불가. Core ML은 실행 엔진이라 LLM 학습 수단이 아님. 반면 Create ML `MLWordTagger`는 Mac에서 토큰 태거를 학습해 `.mlmodel`로 내보낼 수 있고, iOS 17+에서 `NLModel`로 돈다. 합성 데이터 실험(본 보고서)으로 가능성과 한계를 쟀다.

## 선택지
| 선택지 | 장점 | 단점 |
|---|---|---|
| A. 아무것도 안 함(서버 사전 + AI만) | 단순, 정본 하나 | 오프라인·미리보기 없음, 새 표기·신조어는 AI 옵트인 사용자만 |
| B. FM 어댑터 파인튜닝 | 설명까지 온디바이스 | 툴킷 26.0.0 종료·iOS 27 비호환, iOS 26+ & Apple Intelligence 기기만 |
| C. 자체 sLLM(LoRA → MLX) | 설명까지 | 14번 §15-6 트랙, 무겁고 iPhone 불가, S6 이후 |
| **D. Create ML 스팬 태거(CRF/BERT) + 사전 우선 하이브리드** | 0.45~1.5 MB, iOS 17+, 네트워크 0, 학습 10분 이내, 사전 밖 표기 F1 0.06→0.90 | 일반 명사 오탐 위험, 사전과 모델 이중 관리, 설명은 못 함 |

## 결정
D를 **v1.1 실험 플래그**로 채택 후보로 둔다. 앱 `Domain`에 `JargonDetecting` 프로토콜, `Platform`에 `JargonDetector`(NaturalLanguage/Core ML) 구현, 모델은 번들 리소스. 결과는 **미리보기·오프라인 힌트**로만 쓰고 저장하지 않으며, 서버 응답(사전 우선 + 인덱스 재계산)이 오면 교체한다. 병합 규칙 = 사전 스팬 우선, 모델 스팬은 확률 ≥ 0.9이고 더 길 때만 대체/추가. v1.0에는 넣지 않는다.

## 근거
- 합성 실험(3-gram 중복 0): 사전 단독 ALL F1 0.673 → 하이브리드(W-BERT v3) 0.930, 사전 표기 구간 1.000 유지, 사전 밖 새 표기 0.900·신규 용어 0.858.
- iOS 17 최소 OS와 정확히 맞음(BERT 모델 `availability` iOS 17.0, CRF iOS 12.0). Mac p50 8 ms(BERT)/0.07 ms(CRF).
- 원문이 기기 밖으로 안 나감 → ADR-0008·REQ-33과 충돌 없음, App Privacy 변화 없음.

## 결과 (쉬워지는 것 / 어려워지는 것)
- 쉬워짐: 오프라인 탐지, 서버 왕복 전 형광펜, 비옵트인 사용자에게도 "사전 밖 판교어 후보" 표시, (v1.2) 신규 용어 후보 수집으로 사전 보강.
- 어려워짐: 사전 버전 ↔ 모델 버전 동기화(사전이 바뀌면 재생성), 평가셋에 "⑤ 온디바이스 탐지기" 행 추가 관리, BERT 자산 미설치 기기 폴백(CRF).

## 되돌리는 조건
- 사람 검수 평가셋(§15-2 200문장)에서 하이브리드가 사전 단독 대비 스팬 F1 +0.03 미만, 또는 일반 문장 오탐 > 0.05건/문장, 또는 최저 지원 iPhone p95 > 30 ms → 플래그 off, 사전 이형 표기 보강(서버)만 유지.
- 서버 사전 + 정규화만으로 새 표기 재현율이 0.85 이상이 되면 모델 불필요로 폐기.
