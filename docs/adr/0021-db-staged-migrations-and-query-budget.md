# ADR-0021: DB는 계약 17테이블을 유지하되 v1.0은 8테이블만 만든다 + 요청당 SQL 예산

- 상태: 채택 (2026-10-27)
- 관련: 계약 `contracts/db.dbml` v1.0(불변), ADR-0003(블루그린), ADR-0020(해석 서버), 14번 §6, REQ-20·34, 백로그 #75·#104

## 맥락

- 계약 v1.0 dbml은 17테이블이다. v1.0 기능(로그인·해석·할 일·용어·프로젝트 조회)이 실제로 쓰는 것은 8개다.
  나머지 9개(카드·복습·퀴즈 5, 회의·녹음 2, 기기·알림 2)는 v1.1~v1.2 기능이다.

- 사용자 요구(2026-10-27): "테이블이 너무 많으면 안 된다. 나중에 붙여도 영향 없게. 백엔드는 성능 좋게."
- 계약 파일은 고칠 수 없다(v1.0 고정). 테이블을 합치거나 지우면 계약 위반이다.

## 선택지

| 선택지 | 장점 | 단점 |
|---|---|---|
| 17테이블 전부 지금 만든다(이전) | 단순 | 쓰지 않는 표 9개가 운영·백업·마이그레이션 검사 대상. 쓰지 않는 표에 쓰는 코드(카드 출처 끊기 등)가 매 요청 돈다 |
| 계약을 고쳐 테이블을 합친다(예: 알림+기기, 퀴즈 세션+문항) | 표 수 감소 | **계약 v1.0 변경** — 금지. 합친 표는 인덱스·잠금 범위가 커진다 |
| JSON 컬럼 하나에 몰아 넣기 | 표 수 최소 | 계약 위반, 인덱스·외래 키 없음, 쿼리 성능 나쁨 |
| **계약·모델은 17 그대로, 마이그레이션만 단계화(채택)** | 계약 1:1 유지, v1.0 DB는 8표. 기능이 열릴 때 **추가만** 하는 리비전 → 기존 데이터 영향 0 | 대기 초안이 계약과 어긋날 위험 → 테스트로 막는다 |

## 결정

1. 모델(`app/*/infra/models.py`)은 dbml 17테이블과 1:1을 유지한다(`test_schema_matches_dbml`).
2. 마이그레이션 `0001`은 `app/core/schema.py`의 `ACTIVE_TABLES`(8개)만 만든다:
   `levels, users, projects, terms, term_examples, translations, translation_actions, translation_terms`.

3. 나머지는 `migrations/staged/{learning,meetings,notify}.py`에 대기 초안으로 둔다. 기능을 열 때:
   초안을 `versions/`로 옮겨 리비전을 붙이고 → `ACTIVE_TABLES`에 이름을 더한다 → 그 표를 쓰는 코드 경로가 켜진다.

4. 아직 없는 표를 쓰는 코드는 `schema.has("…")`로 막는다. 막혔을 때 응답은 계약상 맞는 값이다:
   회의 id → `MEETING_NOT_FOUND`, 프로젝트 `meetingCount`·`unknownTermCount` → 0, `inMyCards` → false, 카드 → null.

5. 없는 표를 가리키는 외래 키(`translations.meeting_id → meetings`)는 v1.0 DB에 만들지 않는다
   (MySQL은 없는 표를 참조하는 FK를 만들 수 없다). `meetings` 초안이 표와 함께 그 FK를 붙인다.

6. `alembic check`는 `include_object`로 열린 표와 그 사이 FK만 비교한다.
   `tests/test_staged_migrations.py`가 **"head + 대기 초안 = 계약 17테이블, 차이 0"**과 되돌리기를 매번 확인한다.

## 성능: 요청당 SQL 예산
요청 지연은 대부분 DB 왕복 수가 정한다(MySQL 같은 VPC 왕복 ≈ 0.3~1ms, 문마다 파싱·잠금). 그래서 **문 수**를 기준으로 삼는다.

| 요청 | 전 | 후 | 바꾼 것 |
|---|---|---|---|
| POST /translations | 11 | **6** | 저장 뒤 다시 읽지 않고 응답을 메모리에서 만든다(용어 이름·쉬운 말은 매칭 때 이미 앎) |
| GET /translations/{id} | 5 | **3** | 번역+프로젝트 이름 조인, 할 일 1, 용어 1(카드는 표가 열린 뒤) |
| GET /translations | 2 | 2 | (아래 "되돌린 것") |
| GET /actions | 2 | 2 | 회의 조인은 표가 열린 뒤에만 |
| GET /projects | 2+6N | **3** | 프로젝트마다 6문(N+1) → 표마다 GROUP BY 1문(`project_id IN (…)`) + 창 함수 개수 |
| GET /terms/{id} | 6 | **3** | 조회수 +1을 먼저 하고 용어+작성자 조인 1문으로 읽기(refresh 제거) |

같이 바꾼 것:

- **JWT 키 객체 캐시.** PyJWT에 PEM 바이트를 주면 요청마다 키를 다시 파싱한다(프로파일: 요청당 ~0.5ms, 모든 인증 요청).
- **DB 풀**: 프로세스당 10 + 10, 대기 15초, 1800초마다 새 연결. 블루·그린 5프로세스 × 20 = 100 < MySQL 151.
  해석은 AI 호출(최대 12초) 동안 연결을 쥐므로 대기를 AI 타임아웃보다 길게 둔다.

- `pool_pre_ping`은 유지(빌릴 때 COM_PING 1왕복). DB 재시작 뒤 죽은 연결로 500이 나는 것보다 싸다.

측정(`scripts/bench.py`, 프로세스 안 ASGI, SQLite, 데우기 1회 + 3회 중앙값, 2026-10-27, 같은 기계에서 main과 비교):

| 요청 | main p50 (동시 1) | 후 p50 (동시 1) | main rps (동시 20) | 후 rps (동시 20) |
|---|---|---|---|---|
| POST /translations | 15.3ms | 5.5ms | 79 | 128 |
| GET /translations/{id} | 5.7 | 3.0 | 172 | 257 |
| GET /translations | 11.4 | 3.5 | 148 | 195 |
| GET /actions | 9.2 | 5.2 | 149 | 239 |
| GET /projects | 6.4 | 3.4 | 74 | 227 |
| GET /terms/{id} | 6.3 | 4.3 | 83 | 182 |

SQLite는 쓰기 잠금이 하나라 동시 20의 POST·용어(조회수 UPDATE) p95는 잠금 대기다. MySQL 수치는 스테이징에서 다시 잰다.

### 되돌린 것 (측정으로 기각)

- **목록 개수를 `count(*) over()`로 합치기.** 왕복 1번을 줄이지만 DB가 LIMIT 전에 조건에 맞는 행을 **전부** 읽는다.
  `(user_id, created_at)` 인덱스로 20행에서 멈추던 것이 멈추지 않는다 → 측정에서 110→218ms로 **느려졌다**. 해석 기록·할 일 목록은 따로 세는 COUNT(인덱스만 훑음)로 되돌렸다.
  프로젝트 목록은 사용자당 수 개라 창 함수를 쓴다.

- **할 일 개수를 GROUP BY 파생 표로 붙이기.** 다른 사용자 할 일까지 모은다. 페이지 행(20개)마다 인덱스로 세는 상관 부분질의가 낫다.
- **orjson 응답.** 프로파일에서 JSON 직렬화는 상위에 없었다(`to_api` 0.14s/2만 회). 의존성만 늘어서 넣지 않는다.

## 결과

- 쉬워짐: v1.0 운영 DB는 8표. 기능을 열 때 리비전 하나 + 이름 한 줄. 내릴 때도 그 표만 지운다.
- 어려워짐: 지연 표를 쓰는 코드는 `schema.has` 게이트를 잊으면 v1.0에서 "no such table" 500이 난다 → QA가 `app/` 전체에서 지연 표 참조를 확인했고, 새 참조는 리뷰 체크 항목이다.
- 운영 주의: `meetings` 초안의 FK 추가는 MySQL에서 `translations` 표 복사(COPY) 재구성이다. 표가 크면 점검 창에 돌린다(그때까지 `meeting_id`는 항상 NULL이라 실패하지 않는다).
- 남은 일(v1.1): 해석 요청이 AI 호출 동안 DB 연결을 쥐지 않게 — 읽기(프로젝트·중복 확인·사전) → 연결 반납 → AI → 짧은 쓰기 트랜잭션.

## 되돌리는 조건

- 단계화 자체: 대기 초안 3개가 같은 릴리스에 모두 열리면 하나로 합쳐 옮긴다.
- 문 수 예산: MySQL 스테이징 p95가 200ms를 넘는 요청이 생기면 그 요청부터 EXPLAIN 하고, 필요하면 응답 캐시(Redis)를 검토한다(지금은 사용자별 데이터라 무효화 비용이 더 크다).
