# ADR-0023: 서버에서 문맥으로 판교어를 찾는다 — 사전 우선 + 글자 CRF(python-crfsuite) 보충

- 상태: 채택 (2026-10-27)
- 관련: ADR-0007(AI 4트랙)·0008(원문 외부 전송)·0018(판교어 탐지 실험)·0020(해석 서버), REQ-10·14·20, `ml/pangyo-tagger/REPORT.md` §9

## 맥락

- 지금 서버의 판교어 찾기는 **사전 trie(132개 용어 + 이형 표기) + 경계 규칙**뿐이다
  (`app/decode/domain/matching.py`, `repository.Dictionary.spans`). 사전에 없는 표기(`싱크업`, `디벨롭먼트`, `컨퓸`)와
  사전에 없는 새 말(`어카운터빌리티`)은 하나도 못 찾는다. AI(Gemini)는 옵트인한 사용자에게만 간다(ADR-0008).
- 사용자 요구(2026-10-27): "nanoGPT처럼 **주변 문맥을 보고 확률로** 판교어를 추론하게." 실행 위치는 사용자가 **서버**로 정했다
  (온디바이스 아님). 원문은 우리 서버 밖으로 나가면 안 된다(ADR-0008, REQ-14).
- ADR-0018 실험(합성 데이터, Create ML)에서 **글자 단위 CRF + 사전 우선 하이브리드(확률 ≥ 0.9)**가 가장 싸고 쓸 만했다.
  Create ML은 리눅스(OCI ARM VM)에서 돌지 않으므로 같은 모델을 파이썬으로 다시 만든다.

### 이 모델이 하는 일 (정직하게)
- CRF(조건부 무작위장)는 **판별형 순차 모델**이다. GPT처럼 다음 글자를 생성하지 않는다.
- 글자마다 "판교어 시작(B) / 안(I) / 밖(O)" 라벨을 매기는데, 그때 **왼쪽·오른쪽 ±3글자 창, 글자 2·3-gram, 어절 안 위치,
  받침 유무, 문자 종류 패턴**을 본다. 이웃 라벨끼리의 전이도 같이 학습한다(앞이 B면 뒤는 I일 확률 ↑).
- 출력은 글자마다 라벨의 **주변 확률(marginal)**이다. 스팬 확신도 = 스팬 안 글자 확률의 최솟값. 이게 "문맥 → 확률" 아이디어의 구현이다.
- 한계: 창이 짧아(±3글자 + 어절 특징) 문장 전체의 뜻은 못 본다. 동음이의(축구 `킥오프`)는 여전히 사전이 끌고 온다.

의존성 `python-crfsuite` 0.9.12 (MIT, CRFsuite C 라이브러리 바인딩, 런타임 의존성 0):
- 휠 확인(PyPI, 2025-12-23 배포): `cp312-manylinux_2_28_x86_64`, `cp312-manylinux_2_28_aarch64`, `cp312-macosx_11_0_arm64`.
  Dockerfile 베이스 `python:3.12-slim`(Debian bookworm, glibc 2.36 ≥ 2.28) → `uv sync --frozen --no-dev`가 소스 빌드 없이 휠만 설치한다.
- 대안 `sklearn-crfsuite`(같은 C 라이브러리 + scikit-learn 의존) / CRF++(GPL 계열, 바이너리 배포 번거로움) / 직접 구현(학습기 검증 부담) → 가장 가벼운 원본 바인딩을 쓴다.

## 결정

1. **사전 먼저, 모델은 빈자리만.** 처리 순서: 사전 스팬 → 엔진(Gemini 또는 사전 간이 해석) → AI 새 말 배치(사전과 겹치면 버림)
   → **모델 스팬**(사전·AI 스팬과 겹치지 않는 것만). 사전 표기에 대한 결과는 이전과 바이트 단위로 같다(공유 정답 벡터
   `packages/test-vectors/jargon_match.json` 통과). AI 새 말은 뜻이 있으므로 같은 자리면 모델보다 우선한다.
2. **관문**(모두 미리 정함): 스팬 확신도 ≥ `MWONMAL_JARGON_MODEL_THRESHOLD`(기본 0.9, ADR-0018에서 테스트 전에 정한 값),
   길이 2~30, 한글·라틴·숫자·`&/-:`·낱말 사이 공백 한 칸만, 시작·끝 경계는 사전과 같은 규칙(`same_word`, `ends_word`),
   한글이 없는 문장은 모델을 돌리지 않음(학습 분포 밖), **평범한 말 목록**(`ORDINARY_WORDS`: 서버 사전이 일부러 뺀 말 + 흔한
   사무실 외래어 — 회의록·이메일·마우스·엑셀…)은 버림.
3. **응답 모양(계약 그대로, `contracts/*` 변경 0)**: `termId=null`, `termKo=matchedText`(원문 표기), `plainKo=""`(뜻 모름),
   `confidence`=모델 확률(0~1, 소수 셋째 자리). 저장은 `translation_terms.ai_term_ko/ai_plain_ko`(빈 문자열) → GET도 같은 값.
   쉬운 말 바꾸기(`resultText`)는 모델 스팬을 건드리지 않는다(뜻을 모르므로 원문 그대로).
4. **코드 위치(decode 컨텍스트 안, import-linter 계약 유지)**:
   `domain/jargon_features.py`(특징·BIO 복원·관문·병합, 순수 함수 — 학습 스크립트도 이 파일을 그대로 import),
   `infra/jargon_model.py`(모델 지연 로드 1회, 잠금, 추론), `infra/model/jargon_crf.crfsuite` + `jargon_crf.json`(특징 버전·임계값·
   시드·sha256·지표), `usecases/translate.add_context_spans`.
5. **켜고 끄기**: `MWONMAL_JARGON_MODEL`(기본 1). 0이면, 또는 모델 파일이 없거나 특징 버전·sha256이 안 맞거나 추론이 예외를 내면
   **사전만**으로 돈다(= 이 ADR 전과 같은 응답). 로그는 `jargon_model_unavailable reason=…` / `jargon_model_failed`만, 원문 없음.
6. **학습(재현)**: `ml/pangyo-tagger/train_crf.py`(시드 20261027, 합성 데이터만, 데이터·결과는 커밋 안 함). 두 번 돌려 sha256이 같음을 확인
   (`97b84396…`). 용어표는 **서버 사전에 맞췄다**(`server_terms.py`): 양성 = 서버 132개 용어의 표기, 서버가 일부러 뺀 말(회고·배포·지표·
   스프린트·이슈·미팅…)은 학습 하드 네거티브, 실험 사전에만 있는 외래 업무어 10개는 "신규 용어" 평가 전용.

### 숫자를 만든 과정 (보고 고친 것)
- 1차 학습(실험 어휘 + 서버 정렬만): 서버 하이브리드 ALL 0.914, hardneg3 FP **28**, 오탐 예 `마우스`·`스마트폰`·`백업`·여는 말 `번거로우시겠지`.
- 그 실패를 보고 **평범한 말 어휘를 새로 써서**(일상 외래어·일상어 157개, 짝수 = 학습 / 홀수 = 새 평가셋 fresh_neg) 학습 네거티브를
  늘렸고(2차), 평범한 말 목록을 붙였다. 2차 hardneg3 FP 28 → 10(목록 없이) → 1(목록). **2차 설계는 1차 테스트 실패를 본 뒤라 hardneg3
  숫자는 그만큼 낙관적이다.** 이를 덜려고 새 평가셋(fresh_neg)을 만들어 학습·목록과 어휘를 분리했다(`train_crf.py`가 겹침을 assert).
  여는 말 `-시겠지만` 꼴은 학습에 넣지 않고 fresh_neg 에만 두었다.

### 지연·크기
- 모델 177 KB(목표 2 MB 이하), 로드 ~9 ms(첫 요청 1회), 학습 5~20초(기계 부하에 따라).
- 추론(`add_context_spans`, 프로세스 안 1,000회): 19자 p50 0.19 ms / 48자(계약 예시) p50 0.55 ms / 420자 p50 4.6 ms·p95 11.7 ms
  (입력 상한 500자). 측정 중 기계 load average 80~150(다른 작업과 공유)이라 실제보다 느리게 나왔을 수 있다.
- `scripts/bench.py --requests 200 --concurrency 1 --rounds 3`(POST /translations, SQL 6문 그대로): 3회씩 번갈아 돌렸다(main / 이 브랜치 켬 / 이 브랜치 끔).

  |---|---|---|---|---|
  | 1 (78→166) | 8.6 ms | 30.9 ms | 7.9 ms | 2.3 / 3.8 / 6.9 ms |
  | 2 (113→36) | 8.2 ms | 6.5 ms | 16.3 ms | 4.0 / 1.8 / 40.9 ms |
  | 3 (238→111) | 17.8 ms | 17.5 ms | 45.0 ms | 6.5 / 8.3 / 25.2 ms |

  믿을 수 있는 숫자는 위 프로세스 안 측정(벤치 문장 19자 기준 요청당 **+0.19 ms**)이다. 조용한 기계·스테이징에서 다시 잰다.

## 결과 (쉬워지는 것 / 어려워지는 것)

- 쉬워짐: 옵트인 안 한 사용자도 사전 밖 표기·새 말을 **후보로** 본다(합성 기준 ALL F1 0.615 → 0.904, 정밀도 1.00 유지). 원문은 서버 밖으로 안 나감.
  사전에 넣을 후보를 고르는 근거(모델이 자주 잡는 `termId=null` 표기)가 생긴다.
- 어려워짐: 사전이 바뀌면 모델도 다시 학습해야 한다(`train_crf.py --export`, 20초 안쪽, 결정적). 특징을 바꾸면 `FEATURE_VERSION`을 올려야
  한다(안 맞으면 서버가 모델을 끈다).

| 2차 설계가 1차 테스트 실패를 보고 나옴 | 중 | hardneg3 숫자는 낙관적. fresh_neg를 따로 만들어 분리했지만 이것도 같은 생성기 |
| 띄어 쓴 새 표기·짧은 새 표기 놓침(`탑 다운`, `벞퍼`, `대일리`), 조사까지 잡음(`톱다운피드백이`) | 중 | 재현율 0.46~0.80. 놓치는 쪽은 사전만일 때와 같으므로 해는 없다 |
| 동음이의(축구 `킥오프`) | 중 | 사전이 끌고 오는 문제라 이번 변경과 무관(함정 FP 1 = 사전) |
| 긴 입력의 CPU 시간이 이벤트 루프를 잡음(500자 ~5 ms) | 낮음 | 입력 상한 500자. 커지면 `run_in_threadpool`로 옮긴다 |
| 이모지·결합 문자 | 낮음 | 서버가 NFC로 바꾼 뒤 스칼라 인덱스로 계산(테스트: 피부색 수식자 이모지 뒤 인덱스, NFD 입력). 이모지·문장부호가 낀 스팬은 버린다. 이모지 근처에서 확신도가 낮아진다(0.998 → 0.906) |
| 모델 파일 손상·버전 불일치 | 낮음 | sha256·특징 버전 확인 실패 시 사전만(테스트 있음) |
| 스레드 안전 | 낮음 | crfsuite Tagger 호출 전체를 잠금 안에서(8스레드 동시 테스트 = 순차 결과) |

## 되돌리는 조건

- 사람 검수 평가셋(실제 같은 문장)에서 서버 하이브리드가 사전만보다 스팬 F1 +0.03 미만이거나, 평범한 문장 오탐이 0.05건/문장을 넘고
  앱이 "추정" 표시를 하지 못하면 → `MWONMAL_JARGON_MODEL=0`(배포 없이 설정만으로 즉시 사전만으로 돌아감).
- 운영에서 `jargon_model_failed`가 반복되거나 POST /translations p95가 모델 때문에 20 ms 넘게 늘면 → 끈다.
- 완전히 지울 때: `add_context_spans` 호출 한 줄, `jargon_model.py`·`jargon_features.py`·`model/`, 의존성 `python-crfsuite`를 지운다. 계약·DB 변경이 없으므로
  저장된 모델 스팬(`term_id=NULL`)은 AI 새 말과 같은 모양으로 남는다.
