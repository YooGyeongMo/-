# ADR-0013: 한 번에 다 내지 않고 롤링 릴리스(v1.0~v1.4)로 낸다. v1.0 = iPhone 해석, 2026-11-20(금)

| 항목 | 값 |
|---|---|
| 상태 | 채택 (2026-10-25, 사용자 결정: "조금 미루는데 그 대신 빡빡하게 간다") |
| 관련 REQ | REQ-34(컷 항목 삭제 금지, 날짜만 배정), REQ-20, REQ-30 |
| 대체 | 16번 v2 §4·§5(34일 × 8h 계획), FD-8의 11/6·11/13 날짜 |
| 영향 문서 | `docs/16_실행계획.md` §0(v3), `docs/STATE.md`, GitHub 마일스톤 |

## 1. 의도
실제 가용 시간(하루 2~3시간, 2026-09-27 본인 확인)으로 **출시를 실제로 해내는** 계획을 만든다. 범위를 버리지 않고(REQ-34) 날짜만 다시 배정한다.

## 2. 비용
- 기존 계획 264h vs 11/6까지 가용 20~30h(10/26~11/6 평일 10일). 격차 9배 → 날짜를 지키는 방법은 없다.
- 채택안: 평일 하루 **3h**(가용 상한) 고정. v1.0 = 20일 × 3h = **60h**. 버퍼는 Day 20 하루뿐("빡빡하게").
- v1.1~v1.4 합계 115h → 40일 → 2027-01-19. 전체 완료 시점은 대안 (나)와 비슷하지만 **첫 출시가 11/20**이다.

## 3. 대안
| 대안 | 탈락 이유 |
|---|---|
| (가) 11/6 유지 + 범위 극단 축소(서버 배포 빼고 해석만) | 20~30h로는 로그인·해석·배포 중 하나도 끝까지 못 간다. 실사용자 0 |
| (나) 전 범위를 한 번에, 2027-02 말 출시 | 4개월간 사용자 피드백 0. 중간에 동기 붕괴 위험이 가장 큼 |
| (다) 하루 2h로 여유 있게, v1.0 = 12/4 | 사용자 지시("빡빡하게")와 다름 |
| **(라) 롤링, 하루 3h, v1.0 = 11/20 (채택)** | — |

## 4. 왜
가치 70%가 "붙여넣기 → 해석"(T-D2)에 있으므로 그것만 먼저 실사용자 손에 넣는다. 녹음·복습·넓은 레이아웃은 해석 경로 위에 얹히는 기능이라 뒤로 미뤄도 다시 짤 코드가 거의 없다. 계약 v1.0(43 op)은 그대로 두고 **구현만** 나눠서 하므로 계약 수정이 필요 없다.

## 5. 릴리스
| 릴리스 | 마감 | 내용 | 예산 |
|---|---|---|---|

12/25·1/1은 쉰다(계산에 반영).

**순서 원칙 (2026-10-25 사용자 지시)**: iPhone → iPad → macOS. 플랫폼은 iOS(휴대폰) 기준으로 맞추고, iPad는 그다음, macOS는 마지막에 따로 낸다. iPad와 macOS를 한 릴리스에 묶지 않는다(넓은 레이아웃은 iPad에서 먼저 굳히고 macOS가 재사용).

## 6. 검증
- 매주 금요일 15분 회고: 그 주 실제 시간 합계와 남은 Day를 `docs/log/`에 1줄로 남긴다.
- 금요일 기준 Day가 **2일 이상** 밀리면 아래 7번을 바로 발동한다.

## 7. 리스크·되돌리는 조건
- **버퍼가 하루뿐.** 밀리면 컷 순서: ① 평가셋 50문장(Day 9) → 백로그 ② 홈 기록 목록(Day 13) → 결과 화면 하나로 ③ 마지막으로 날짜를 11/27로 이동.
- TestFlight **외부** 테스터는 베타 심사(보통 1일 내외)가 필요하다. 11/20엔 **내부 테스터**로 내고, 외부 심사는 같은 날 제출만 한다.
- Gemini 무료 한도·약관이 바뀌면 v1.0은 사전만(`none` 엔진)으로 낸다(ADR-0008).
