## A. 산출물과 계약의 층위 (기술서 · API 명세 · DB 스키마)

### T-A1. 계약 우선(contract-first) vs 코드 우선(code-first)
| | 계약 우선 (yml이 원본) | 코드 우선 (FastAPI가 스키마 생성) |
|---|---|---|
| 장점 | 앱·서버가 같은 문서를 봄, 심사·발표 자료가 곧 계약, 코드 생성 | 서버 개발이 빠름, 문서와 코드가 자동 일치 |
| 단점 | yml과 라우터를 둘 다 유지, drift 위험 | 앱이 서버 완성을 기다림, 스키마가 구현 세부에 끌려감 |
**결정: 계약 우선.** 근거: 앱과 서버를 혼자 번갈아 만들기 때문에 앱은 Prism 목 서버로 먼저 가야 하고, 제출한 yml이 이미 43개를 정의했다. drift는 `schemathesis` + 스키마 diff 테스트로 막는다(13번 §4). **되돌리는 조건**: 없음. 계약을 버리면 두 클라이언트(iOS, macOS)가 서버에 종속된다.

### T-A2. DB 스키마의 원본: dbml vs Alembic 마이그레이션
**결정: dbml은 "설계 문서", 마이그레이션이 "실행 원본".** dbml은 초기 마이그레이션의 씨앗이고 이후 변경은 마이그레이션 → dbml 역반영(문서 갱신)이다. 근거: 운영 DB의 진실은 마이그레이션 이력뿐이다. **되돌리는 조건**: dbml에서 마이그레이션을 자동 생성하는 도구를 CI에 붙일 수 있게 되면 dbml을 원본으로 승격.

### T-A3. 화면 설계의 "웹 10장"을 어떻게 구현하나
| | 브라우저 웹 앱 (React 등) | macOS 네이티브 (SwiftUI) | 둘 다 |
|---|---|---|---|
| 재사용 | 앱과 코드 공유 0 | ViewModel·Domain·SDK 전부 공유 | 최악 |
| 도달 | 어디서나, 설치 없음 | Mac 사용자만 | 최대 |
| 온디바이스 AI·STT | 없음 | 있음 | |
| 비용 | 두 번째 스택 | 한 스택 | 두 스택 |
**결정 D-0: macOS 네이티브.** 근거: 혼자, 한 스택, 온디바이스 기능. **되돌리는 조건**: 윈도우 사용자 요구가 실제로 생기면 같은 API로 웹을 추가(계약이 있어 가능). 그때도 macOS 앱은 버리지 않는다.

### T-A4. 기술서(개요 PDF)와 구현이 달라지는 부분을 어떻게 다루나
**결정**: 기술서는 제출본으로 고정하고, 달라진 결정은 이 문서와 12·14번에 "제출본과의 차이"로 남긴다. 현재 차이: 웹→macOS(D-0), OCR 온디바이스(D-6, 계약 변경 없음), 게스트 없음(D-8), 알림 macOS 로컬(D-19). 근거: 심사 기준은 제출본이고, 구현은 그 계약을 지키면 된다.

## B. API 명세 (yml v1.0을 유지하면서 고려한 것)

### T-B1. REST vs GraphQL vs gRPC
| | REST + OpenAPI | GraphQL | gRPC |
|---|---|---|---|
| 클라이언트 생성 | Apple 공식 생성기 | Apollo iOS(무겁고 코드젠 복잡) | swift-protobuf + grpc-swift |
| 화면 단위 조회 | 홈 3호출(병렬) | 1호출로 맞춤 | |
| 캐시·ETag·폴링 | HTTP 그대로 | 별도 층 | HTTP/2 스트림 |
| 심사·문서 | Swagger로 바로 보임 | 스키마 탐색기 | proto |
**결정: REST.** 홈 3호출은 병렬 `async let`로 300ms 안이고, ETag 폴링(W-04)이 HTTP에서 공짜다. **되돌리는 조건**: 화면 하나가 5개 이상 리소스를 조합하게 되면 그 화면만 BFF 엔드포인트(`GET /home`)를 추가한다. GraphQL 전환은 아니다.

### T-B2. 긴 작업(녹음→해석) 전달: 폴링 vs SSE vs WebSocket vs 푸시만
| | 3초 폴링 + ETag | SSE | WebSocket | 푸시만 |
|---|---|---|---|---|
| 서버 복잡도 | 0 | 연결 유지, Caddy 타임아웃 | 상태·재연결 | APNs 의존 |
| 앱 복잡도 | `.task` 루프 | URLSession 스트림 파싱 | 라이브러리 | 앱 열려 있으면 못 받음 |
| 지연 | ≤ 3초 | 즉시 | 즉시 | 즉시(폰만) |
| 비용 | 세션당 ~400회 304 응답 | 연결당 워커 점유 | | |
**결정: 폴링 + ETag(v1), 완료는 푸시 병행.** 근거: 해석은 20분 안에 끝나고 304는 바디가 없어 싸다. **되돌리는 조건**: 동시 폴링 세션 > 200이 지속되면 SSE(`GET /recordings/{id}/events`)를 v1.1에 추가. WebSocket은 양방향이 필요 없어 후보 아님.

### T-B3. 페이지네이션: offset(page/size) vs cursor
**결정: offset 유지(계약 v1.0).** 목록이 사용자 단위 수백 건이라 offset의 중복·누락 문제가 체감되지 않고, `PagedResponse{page,size,totalElements,totalPages}`가 앱 "더 보기"에 딱 맞는다. **되돌리는 조건**: 해석 기록이 사용자당 1만 건을 넘거나 실시간 삽입이 많아지면 `GET /translations`만 cursor 파라미터를 추가(호환 유지).

### T-B4. 에러 모델: HTTP 상태만 vs `code` 문자열 30종
**결정: 둘 다(계약 v1.0).** 상태는 전송 계층, `code`는 행동 결정(D-14). 트레이드오프: 코드가 늘면 앱 매핑도 늘지만, 매핑 테스트가 전수라 안전하다. `message`는 화면에 그대로 띄워도 되는 우리말이라 앱이 문구를 중복 소유하지 않는다.

### T-B5. 날짜·시간: 오프셋 없는 ISO 8601(v1.0) vs `+09:00`/UTC
| | 오프셋 없음 (현재) | `+09:00` | UTC `Z` |
|---|---|---|---|
| 표준 파서 | 실패 (앱 D-13에서 커스텀 변환) | 통과 | 통과 |
| 가독성 | 한국 사용자에게 자연 | 자연 | 9시간 차이 |
| 해외 사용자 | 깨짐 | 정확 | 정확 |
**결정: v1.0은 커스텀 변환으로 감당, v1.1에서 `+09:00`.** 이유: 제출본을 지키되 표준 파서 호환은 회복해야 한다. **되돌리는 조건**: 없음, v1.1은 확정.

### T-B6. 인증: JWT vs 불투명 세션 토큰, refresh 유무
| | JWT (RS256) | 불투명 토큰 + 서버 조회 |
|---|---|---|
| 검증 | 서버 무상태, 키만 | 요청마다 Redis/DB |
| 폐기 | 만료 전 즉시 폐기 어려움 | 즉시 |
| 앱 | 저장만 | 저장만 |
**결정: JWT, 수명 24h, refresh는 v1.1.** 트레이드오프를 정직하게: refresh 없음은 60분 녹음 중 만료 위험을 만들었고, 앱은 조각 디스크 큐로 유실만 막는다(12번 §7). 즉시 폐기가 필요한 순간(계정 삭제, 도난)은 `kid` 회전 + 짧은 수명으로 대응. **되돌리는 조건**: v1.1 refresh 도입과 함께 액세스 1h로 단축.

### T-B7. 비멱등 POST의 재시도: Idempotency-Key vs 재시도 금지
**결정: v1.0은 자동 재시도 금지(D-12), v1.1에서 키 도입.** 근거: 해석 1건이 AI 비용이라 중복 생성은 돈이다. 사용자 버튼 재시도는 사용자가 결과를 보고 판단하므로 중복이 나도 의도된 것이다.

### T-B8. 파일 업로드: 서버 경유 multipart vs presigned URL 직접 업로드
| | multipart → 서버 → S3 | presigned URL → S3 직접 |
|---|---|---|
| 서버 부하 | 조각 1MB × 60 통과 | 0 |
| 계약 | 단순(현재) | 2단계(URL 발급 + PUT + 완료 통지) |
| 동의·검증 | 서버가 첫 조각에서 동의 검사 | 별도 API 필요 |
| 백그라운드 업로드(iOS) | 생성 클라이언트 한계 | background URLSession 가능 |
**결정: v1.0 multipart 유지.** 근거: 계약 단순, 동의 검사가 한 요청에 묶임, 부하는 §8 용량 안. **되돌리는 조건**: 동시 녹음 > 50이거나 iOS 백그라운드 업로드 실패율 > 2%면 presigned 방식 추가.

### T-B9. 버전 관리: URL(`/v1/`) vs 헤더 vs 계약 버전만
**결정: URL 프리픽스 없음, `info.version` + `User-Agent contract/x.y`로 협상(v1.1 426).** 근거: 클라이언트가 우리 앱 둘뿐이라 호환 깨는 변경은 앱 강제 업데이트로 처리하는 게 URL 분기보다 싸다. **되돌리는 조건**: 외부 클라이언트(웹, 파트너)가 생기면 `/v2/` 프리픽스.

### T-B10. 응답 봉투(envelope) vs 평면 응답
**결정: 평면(현재).** `{data, error}` 봉투는 생성 클라이언트가 옵셔널 지옥이 된다. 에러는 상태 코드 + `Error` 바디로 충분.

### T-B11. nullable + allOf(참조 + null 허용) 표기
**결정: 유지하되 `type` 형제를 넣어 린트 통과(제출본 반영).** 생성 코드가 `value1` 래퍼가 되는 비용은 Mapping 한 층으로 흡수. **되돌리는 조건**: OpenAPI 3.1로 올리면 `oneOf: [ref, null]`로 정리.

### T-B12. enum 값이 한글(`JobGroup: 개발, 기획…`)
트레이드오프: 화면 표시가 공짜지만 코드 식별자·URL·로그에 한글이 들어간다. **결정: v1.0 유지, v1.1에서 `DEV, PM, DESIGN…` 코드 + 표시명 분리.** 앱은 지금부터 표시 문자열을 enum 케이스가 아닌 매핑 표에서 가져온다(바꿀 때 한 곳).

### T-B13. 배치 엔드포인트(`POST /cards/bulk`)와 단건의 공존
**결정: 유지.** 결과 화면 "모두 카드로"가 한 번에 N개를 담으므로 N번 호출은 UX·비용 모두 나쁘다. 단건은 명세에 남기되 앱은 부르지 않는다.

### T-B14. 게스트(비로그인 3회)
트레이드오프: 전환율에는 좋지만 식별(`X-Guest-Id`), 남용 방지, "저장 안 함" 보장, App Store 심사 설명이 다 따라온다. **결정 D-8: 앱 v1 없음.** 계약과 서버 코드는 남긴다. **되돌리는 조건**: 스토어 전환율이 문제로 확인되면 iOS에만 도입(Keychain UUID 식별).

## C. 프론트 공통 (iOS·macOS)

### T-C1. UI 스택: SwiftUI vs UIKit/AppKit vs 크로스플랫폼(KMP·Flutter·RN)
| | SwiftUI only | UIKit+AppKit | Flutter/RN | KMP(공유 로직) |
|---|---|---|---|---|
| 두 OS 한 코드 | 예 (sidebarAdaptable) | 두 벌 | 예 | 로직만 |
| 온디바이스 프레임워크 | 직접 | 직접 | 브리지 | 직접(Swift UI 따로) |
| 채용 시장(iOS) | 표준 | 레거시 강점 | 다른 트랙 | 드묾 |
| 한계 | 부분 범위 탭, keep-all | 없음 | 네이티브 감 | |
**결정: SwiftUI만.** 한계 둘은 우회책이 있다(12번 §9 규칙 9·Typography). **되돌리는 조건**: 특정 화면이 SwiftUI로 성능·기능이 안 나오면 그 뷰만 `UIViewRepresentable`. 전체 전환은 없다.

### T-C2. 최소 OS: iOS 26/macOS 26 only vs iOS 17+
| | 26 only | 17+ |
|---|---|---|
| 얻는 것 | SpeechAnalyzer, Foundation Models, `sidebarAdaptable`, `@Entry`, Swift Testing 통합 | 사용자 도달 최대 |
| 잃는 것 | 출시 첫해 미업데이트 기기 | 온디바이스 AI·STT 전부 서버 의존, 조건 분기 |
**결정: 26 only.** 근거: 이 앱의 차별점(온디바이스 미리보기·OCR·비용 0)이 26 API에 있고, 목표 사용자(판교 IT 신입)는 최신 기기 비율이 높다. **되돌리는 조건**: 출시 6개월 뒤 26 점유율 < 70%면 `@available` 분기로 25 지원.

**폐기 2026-09-21 → FD-1 / ADR-0005 (REQ-02 "다 대비해").** 표 정정: "17+면 `@Entry`를 잃는다"는 **오류** — `@Entry`는 iOS 13+/macOS 10.15+ back-deploy(Xcode 16 툴체인)라 D-3 그대로. Swift Testing도 툴체인 문제(iOS 17 시뮬 실행은 Day 1 확인). 재결정(REQ-20 순서):
1. **의도**: REQ-02(도달 범위)를 지키면서 12번 구조(MVVM-C, "ViewModel에 `#if os()` 금지")를 깨지 않는다. 26 기기에선 26 기능을 살리되 17~25는 같은 화면·같은 VM으로 "덜 화려한 같은 상태".
2. **비용**: 돈 0(iOS 17.0 런타임은 개발 Mac에 설치됨, 공개 저장소 hosted 러너 무료). 시간 0.25(타깃·ADR) + 1.0(루트 2벌, ADR-0006) + 0.5(iOS 17 스냅샷 서브셋). 복잡도: 두 구현을 유지하는 API는 소수(12번 §18 표). 유지보수: 스냅샷 OS별 폴더.
3. **대안**: ① 26 only 유지 — REQ 위반, 탈락. ② 18/15 최소 — 분기 3개 줄지만 REQ 명시값과 다름, 탈락(되돌림 조건으로만). ③ 16 이하 — `@Observable`·`PhaseAnimator`·`ContentUnavailableView`가 사라져 D-15 재작성, 탈락. ④ 화면마다 게이트 허용 — Presentation에 `#available` 산재, 탈락. **⑤ 17/14 + 세 곳 게이트(채택)**.
4. **왜**: 17은 12번이 전제한 관용구(`@Observable`, `.task(id:)`, `RouteHost`)가 전부 들어온 첫 버전이라 코드가 한 줄도 안 바뀌고, 실제 폴백 필요 API는 7개(SpeechAnalyzer·FM·sidebarAdaptable·Liquid Glass·zoom 전환·Mutex·lineHeight)뿐이며 전부 Platform·MwonmalUI/Compat 안에 가둘 수 있다. 미리보기·FM·글래스는 v1.0 범위 밖(FD-8)이라 "차별점" 근거 자체가 v1.0에서 사라졌다.
5. **영향**: `Project.swift` 전 타깃 `.multiplatform(iOS:"17.0", macOS:"14.0")`(+ Domain watchOS 10.0), 12번 머리말·§18·§8·§9·§11, `.swiftlint.yml` `no_available_in_core`, 이 문서 §I #9·§J 행, 이슈 #2·#5·#10·#19.
6. **검증**: `tuist generate` 후 iOS 17.0·26.4 시뮬·Mac 빌드 3회, 린트 0건, `available-audit.sh` diff 0, 스냅샷 Tier1/Tier2(13번 §4).
7. **리스크·되돌림**: 17 사용자는 미리보기 없음(D-7이 정의한 상태 안). 17·26 렌더 차이는 OS별 기준 이미지로 흡수. 되돌림: 출시 6개월 후 iOS 17 < 3% **그리고** 18 전용 폴백 유지비 > 반나절/스프린트 → 최소 18/15. 26 only로는 돌아가지 않는다.

### T-C13. 레이아웃 축: 플랫폼 vs 창 폭 vs 사이즈 클래스 (신설 2026-09-21, FD-2, ADR-0006)
1. **의도**: REQ-01(iPad = macOS와 같은 넓은 레이아웃, iPhone = 세로 접기)과 REQ-03(SE~6K, 고정 px 금지)을 **규칙 하나**로. iPad 창 모드·Split View·Slide Over·회전·Mac 창 크기 변화를 전부 같은 규칙이 처리.
2. **비용**: `MwLayout(h:v:)` 순수 함수 + 환경값 하나 + 루트 switch 1개(0.5일, AdaptiveRoot 1.0일에 포함). 유지보수: 분기점이 한 곳. 돈 0.
3. **대안**: (a) `UIDevice.userInterfaceIdiom == .pad` — Slide Over/1/3에서 compact인데 사이드바를 그림, Mac엔 `UIDevice` 없음, 탈락. (b) 창 폭 임계값(≥ 700pt) — 기기·OS마다 사이즈 클래스 경계가 달라 Apple이 계산한 값을 다시 만드는 바퀴 재발명(REQ-23), HIG "앱은 멀티태스킹 구성을 알 수 없다", 탈락(AdaptiveRoot 한 곳의 보조 임계값도 두지 않음). (c) `horizontalSizeClass`만 — iPhone Pro Max 가로가 `.regular`라 사이드바가 뜸, REQ-01 위반, 탈락. **(d) `horizontalSizeClass == .regular && verticalSizeClass == .regular`(채택)**.
4. **왜**: iPad 전체화면·13" 1/2·Mac은 둘 다 regular, iPhone은 어느 방향이든 하나는 compact, iPad Slide Over/1/3은 가로 compact. Apple 문서가 "Slide Over·Split View에 따라 바뀐다", "macOS는 항상 regular"를 보증하는 값이라 Mac 추가 분기가 없다.
5. **영향**: 12번 D-2 개정·§8(루트 2벌)·§9 Layout·§19, MwonmalUI `MwLayout`, Composition `AppRootView`, Navigation `AdaptiveRoot`, 스냅샷 Tier2(Pro Max 가로·Split).
6. **검증**: 4조합 단위 테스트, Navigation compact↔wide 상태 보존 테스트, 스냅샷(Pro Max 가로 = 사이드바 없음, 11" 1/2 = 탭바, 13" 1/2 = 사이드바).
7. **리스크·되돌림**: iPadOS 26 창 모드의 아주 작은 창이 세로 compact가 되는지 확인 필요(되면 탭바 — 의도된 동작). 11"/13" 1/2 Split의 사이즈 클래스는 확인 필요. 되돌림: Apple이 iPad 사이즈 클래스 의미를 바꾸면 창 폭 보조 규칙 + 히스테리시스(±40pt) 추가.

3. **대안**: (a) self-hosted를 PR 기본(iOS.md·ADR-0002 원안) — 과금 전제가 틀렸고(공개 무료) 보안 경로 열림(RT-B-20), 탈락. (b) hosted만 — `macos-14` 없음·iOS 17.0 런타임 다운로드 5~10분 불확실, 탈락. (c) Xcode 핀 26.5(QA 초안) — 사용자 보유 26.4와 달라 첫 PR부터 스냅샷 diff, 탈락. **(d) PR = hosted `macos-26` + Xcode 26.4, self-hosted = `push main`·`schedule`·`workflow_dispatch`만(채택)**.
4. **왜**: 로직 버그는 OS 무관이라 PR은 한 축(iPhone 17 iOS 26.4 + Mac 26)이면 되고, `@available` 폴백·레이아웃 깨짐은 최소 OS·극단 화면에서만 나오니 야간 Tier2(SE iOS 17.0·Mac 14 VM·iPad·6K·AX·reduceMotion)로 돈다. self-hosted는 PR 이벤트에 절대 배정하지 않으면 fork 코드가 개발 Mac에 닿지 않는다.
5. **영향**: ADR-0002 supersede → ADR-0011, 13번 §5-1·§4, 16번 §1 CI 행·§1-1, `.github/workflows/app.yml`(v2)·`app-nightly.yml`(신규), 이슈 NEW-1·NEW-23·24.
6. **검증**: `pull_request` 트리거에 self-hosted 라벨 0건(grep 테스트), PR 워크플로 p50 ≤ 15분(주 1회 기록), 야간 실패 시 자동 이슈, 릴리스 체크리스트 A-11·A-12.
7. **리스크·되돌림**: hosted `macos-26`에 Xcode 26.4가 없거나 사라지면 → 스냅샷 기록을 CI 이미지 Xcode로 단일화하고 로컬은 검증만. 동시성 대기가 15분을 넘는 상태가 지속되면 스냅샷 job을 야간으로 더 옮긴다. 비공개 전환은 하지 않는다(REQ-27과 비용).
