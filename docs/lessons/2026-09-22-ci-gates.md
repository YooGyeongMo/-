# 배운 점 — CI가 "돌지 않는" 네 가지 방식 (2026-09-22)

> REQ-21. 형식: 상황 → 배운 것 → 다음부터 규칙. 근거: run 35596832770·35415016943·35596832971·35659350657, PR #84·#85.

증상은 하나였다 — "PR은 초록인데 main은 빨갛고, 어떤 건 아예 안 돈다." 원인은 네 개였고 전부 달랐다.

## 1. 게이트가 PR을 건너뛰면 그것은 게이트가 아니라 사후 통보다
- **상황**: `server.yml` image job의 trivy 스텝에 `if: github.event_name == 'push'`가 붙어 있었다. PR에서는 스캔이 아예 실행되지 않으니 언제나 초록, 머지 직후 main에서 처음 돌아 실패했다(9/19·9/21 두 번).
- **배운 것**: 품질 게이트를 "머지 후"에 두면 막는 기능이 사라지고 main을 빨갛게 만드는 기능만 남는다. 되돌리는 비용이 가장 비싼 지점에서 처음 실행된다.
- **규칙**: 머지를 막아야 하는 검사는 **PR에서 반드시 실행**한다. push 전용 스텝은 "배포·게시"처럼 PR에서 의미가 없는 것만. 새 job을 추가할 때 "이 검사는 PR에서 도는가?"를 체크리스트로 묻는다(13번 §4).

## 2. 우리가 고칠 수 없는 취약점으로 파이프라인을 막지 않는다
- **상황**: trivy가 `python:3.12-slim`(Debian 13)의 CVE-2026-76642(util-linux 계열 6개 패키지)로 실패했다. 상태는 전부 `affected` — **수정본이 아직 없음**. `ignore-unfixed` 기본값이 false라 업스트림이 패치를 내기 전까지 영구히 빨간 상태였다.
- **배운 것**: 취약점 게이트의 목적은 "행동 가능한 것을 막는 것"이다. 조치할 방법이 없는 실패는 신호가 아니라 소음이고, 소음이 계속되면 팀은 빨간 CI를 무시하기 시작한다.
- **규칙**: 이미지 스캔은 `ignore-unfixed: true`(수정본이 나온 CVE는 그대로 차단 — 베이스 이미지 갱신으로 해결 가능하므로). 수정본 없는 HIGH/CRITICAL은 막지 말고 **주기적으로 목록만 확인**한다. 베이스 이미지 갱신은 별도 이슈로.

## 3. 존재하지 않는 러너를 요구하는 job은 실패하지 않는다 — 영원히 기다린다
- **상황**: `nightly` job의 조건이 `if: github.event_name != 'pull_request'`였는데, 이건 **push(main)에서도 참**이다. 대상은 `[self-hosted, macOS]`인데 등록된 러너는 0대(`/actions/runners` → `total_count: 0`)였다. job은 실패하지 않고 큐에 앉아 run 전체의 결론을 오염시켰다(9/21 21:49Z 스케줄 run은 다음 날까지 queued).
- **배운 것**: `!= 'pull_request'`는 "schedule만"이라는 뜻이 아니다. 그리고 self-hosted job의 실패 모드는 "에러"가 아니라 "무한 대기"라서 로그만 보면 원인이 보이지 않는다.
- **규칙**: 이벤트 조건은 **허용 목록으로** 쓴다(`== 'schedule' || == 'workflow_dispatch'`), 부정으로 쓰지 않는다. 인프라가 아직 없는 job은 저장소 변수로 잠근다(`vars.SELF_HOSTED_MAC == 'true'`) — 러너를 붙인 뒤 `gh variable set`으로 켠다. self-hosted job을 추가할 때 러너 등록 여부를 먼저 확인한다(ADR-0011).

## 4. push 경로 필터에 워크플로 자신을 넣지 않으면 CI 수정이 검증되지 않는다
- **상황**: PR #84로 위 세 개를 고쳐 머지했는데 **main에 run이 하나도 생기지 않았다**. push paths가 `apps/**`·`services/**`만 보고 `.github/workflows/*.yml`을 뺐기 때문이다. main의 CI 배지는 며칠 전 실패에 멈춘 채였고, `contracts`는 push 트리거 자체가 없어 main에서 한 번도 돈 적이 없었다.
- **배운 것**: 경로 필터는 비용을 아끼지만, 워크플로 자신을 빼면 "CI를 고쳤다"를 증명할 방법이 사라진다. main의 상태 표시는 최신 커밋이 아니라 **마지막으로 트리거된 커밋**의 것이다.
- **규칙**: 모든 워크플로의 push·pull_request paths에 **자기 자신과 자신이 읽는 설정 파일**(`.swiftlint.yml`, `.swiftformat` 등)을 포함한다. 모든 워크플로에 `workflow_dispatch`를 둬서 커밋 없이 검증할 수 있게 한다. CI를 고친 PR은 **머지 후 main run이 실제로 생겼는지**까지 확인해야 끝난 것이다.

## 곁가지: 움직이는 표적과 일시 장애를 구분한다
- `aquasecurity/trivy-action@master`는 버전이 움직여 재현이 안 된다 → `v0.36.0` 고정(예전에 `@0.28.0`이 404였던 건 태그에 `v` 접두사가 필요해서였다).
- 9/19 실패는 위와 완전히 다른 원인이었다: 취약점 DB를 `mirror.gcr.io`에서 받다가 `BLOB_UNKNOWN`(레지스트리 일시 장애). **같은 job이 빨갛다고 같은 원인이 아니다** → 실패마다 로그를 따로 읽고, DB는 ghcr 우선 + mirror 폴백으로 이중화.
- 문서만 바꾼 PR에 "no checks"가 뜨는 것은 경로 필터의 정상 동작이다. 필수 검사(required checks)를 켤 때는 이 경우 머지가 막히지 않도록 주의한다.
